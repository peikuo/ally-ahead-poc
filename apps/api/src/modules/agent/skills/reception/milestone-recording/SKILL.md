【阶段成果】
准备当前交付前，判断本轮是否已做成或谈清具体小目标：有则在同一次交付（communicate或最终回复）附progress，没有则省略。使用本skill不另开总结/判断请求，也不是回复发送后再调用。成果记录只总结已经做过、谈清的小目标，不是plan，不列未解决问题、待办、下一步、索要材料或完成百分比；没有固定阶段、必经顺序或成果总数。
用户明确了真实业务选择、使用范围或约束，或更正已有结论，就应在同轮记录相应具体成果；不要求用户再次确认已说清的意思，不等整个方案完成或出现比较/演练卡。成果记录与回答业务问题并行，不是额外一次总结任务。不能把助手建议当用户同意，也不能把试做一条当真实业务已验证。问候、“好的/继续”、重复旧结论、纯建议或计划不记；无需每轮产生记录，不为了记成果另调模型或强迫确认。
实际比较卡、演练结果和需求草稿由程序从保存内容记为已做的工作；同一回复另谈清了其他小目标才附通知，不为卡片重复通知。索要样例不算完成演练。
有新成果时回复附一个progress：{id,title,summary,evidenceMessageIds:[用户消息UUID]}。id用简短英文/数字/下划线/短横线，自由命名，不能用固定阶段推进；title简短说明具体小目标，summary写实际结论和必要的确定程度（例如“明确疫苗由当班员人工核实”）。依据1—6条本会话实际用户消息；成果里的sourceMessageId/sourceMessageIds是助手产出或选择的来源，不可冒充用户事实依据；不能伪造UUID或借一句“好的”制造新成果。
例如用户明确“想用自己的邮件工具，别人的不一定合适我们”，可记录“明确希望沿用自有邮件工具”，摘要只说本次设计以这一偏好为约束；不能扩大为工具已经支持接入、方案已实施批准、模型已本地部署或邮件数据不外发。此前只是问“怎么设计服务”、助手列出几种建议，不据此记录用户已选定方案。
只在同一业务小目标结论变化时复用上下文已有id，说明最新结论，旧对话依据保留；不为每次措辞变化重复增项。没有新成果就省略progress。用户和你看到同一份最新成果记录。
结合完整对话与成果延续沟通，避免重复问已谈清的事；适时整理需求分析让用户核对、修改，以用户认可为收敛依据，不以目标数量或阶段完成作为结束条件。
