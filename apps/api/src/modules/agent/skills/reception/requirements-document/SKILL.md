---
name: requirements-document
description: 用户明确请求生成或修改需求文档后，依据对话与资料形成可追溯、可验证的轻量需求规格说明书，供企业核对及服务方评估；不自动生成或代确认发布付款。
---

【目的与使用时机】
产出供企业逐项核对、服务方评估范围与工作量的需求规格说明书。它应说明业务需要什么、在什么条件下表现怎样、如何判断满足，而不是聊天摘要或预先选定的技术实施方案。使用用户当前语言，深度随已有信息和业务复杂度调整；信息不足仍可形成明确标出缺口的有用文档，不为凑齐模板强逼追问，不编造项目条件、指标、价格或工期。
只在用户明确要求生成/修改时执行。讨论已足够时可轻量提示，用户可继续聊；引用、能力询问或拒绝生成不是授权，不确定时用requirements_document_offer邀请明确操作。预览、下载或重开复用保存文档。执行前须具备本skill完整正文：明确生成/修改任务由应用加载到当前任务上下文；否则通过read读取，原生历史中已完整读取当前版本则可复用。

【原则一：来源决定一条陈述能承担什么结论】
综合对话时保留每项实质陈述的来源、确定程度与适用范围。客户现状和明确诉求、资料规定、助手建议、推导、实际观察及未知具有不同证据地位；不能因重复出现、措辞肯定或与其他事实并列就互相替代。用户要求整理或确认整稿，不会改变原陈述来自谁、有什么依据；后续明确采纳可记录为决定，同时保留建议来源与采纳依据。采用用户最新明确更正，冲突未解决则列出，不自行替用户裁定。
先厘清支持各项结论的原话或资料，再将其转为需求；不要从先前助手写好的方案反推客户必然需要什么。为文内来源设置可读短标签，给相关原话或资料位置，每条关键需求能回到支持它的具体来源。evidence只使用真实用户messageId与逐字quote；文内资料引用、助手输出和来源标签不能伪装成用户原话。资料须实际授权读取，未读内容不能声称已核实。
明确需求与边界依据已知信息建立；建议另列为可选或待确认，信息缺失保留未知。未讨论某项能力既不证明它必须有，也不证明它被排除。由依据推导的结论注明前提和适用范围，不能比依据更确定或适用更广。

【原则二：需求描述可观察的行为及成立条件】
从业务目标提炼必要的产品行为，用用户故事解释谁在什么场景需要它。每条关键需求只表达一个核心行为，并说明角色/触发、输入或前提、可观察结果，以及影响判断的边界或例外。保留原要求中的条件、限定、角色和确定程度，压缩文字不能改变业务含义；某条件“需要满足”不等于“已满足”，规则推导也不等于实际业务执行或批准。
给关键需求稳定、可引用的文内编号，修改同一需求时尽量沿用，删除或替换注明。编号帮助沟通，不要求固定前缀或固定章节数。人工职责、实施候选和待决事项与产品行为分开；有依据的非功能或数据约束同样说明如何观察，未知指标不补成承诺。服务方仍应能提出实现方式，不替专家确定完整架构。

【原则三：用场景检验需求，而不是给章节贴验收标题】
围绕关键需求组织正常路径和有业务意义的异常/不足条件，并明确引用关联需求编号。验收条件承接同一需求，写出给定条件、动作/输入及可检查的预期结果；可用给定/当/则短条目或表格，并回引需求编号，使来源、需求、场景、验收能贯通。不把“符合要求”“回答准确”等同义重述当成检查办法；已有具体规则或样例时，以其条件和结果表达预期。需要先商定标准时写清待决点及其影响，不自行补标准。
区分验收标准、验证计划和已发生的验证结果。只有实际执行及可核查证据才支持对应结论；文字草稿、演练、工具执行和运行系统是不同验证对象，不能跨层推断。未执行标为待验证，不能由文档生成或用户认可推成已通过。

【原则四：试做是可复核的证据，不是成功标签】
已有相关试做时，保留能复核该观察的最小完整证据：任务与实际输入、所用参考原句/位置、实际输出、必要的计算或规则推导、与预期的对照及局限。材料长时可摘录相关原文，说明摘录范围；不得以泛化总结替代决定结论的细节。原始记录、观察解释与建议改写分开，不能把改进后的答案冒充当时输出，也不能把样例的局部结果当成整体能力。
没有实际试做时可以提出拟议场景，清楚标为建议，不虚构输入来源或执行历史。证据只服务当前业务，不能套用其他案例的规则或条件。

【组织与一致性检查】
依信息自然组织摘要目标、现状范围、用户故事/需求、场景与验收、试做证据、资料边界、人工职责及待决事项；可合并、调整顺序，章节齐全不等于质量合格。建议与未知应便于用户逐项决定，说明对范围或评估的影响，人员和时间只有实际约定才写。
交付前沿每条关键需求核对：来源是否支持这项强度和范围，场景及验收是否检验同一行为，涉及的角色、条件与结果在各处是否一致；试做实际记录是否被保留，结论是否超出观察。发现不一致先收窄或标出待核对，不以更漂亮的措辞掩盖。最终文档提供可核对成果和必要依据，不输出内部推理过程。

【交付与确认】
完整文档用最终interaction：{type:"requirements_document",title,markdown,evidence:[{messageId,quote}],replacesMessageId?}。markdown最多40000字符，evidence最多20条、每条quote最多2000字符。没有可引用的业务事实可留空evidence并把不足写清，不假装需求已齐备。修改旧文档沿用其明确需求并应用用户更正，replacesMessageId由系统根据明确修改来源附加；不要编文档id或版本号。speech只简短说明文档可修改/下载、请用户核对；不要朗读整篇文档或复制一遍Markdown。禁止HTML、脚本、远程资源或执行动作，Markdown只是文档内容。
需要用户同意才生成时，最终interaction={type:"requirements_document_offer",title,prompt}，只是邀请，不是已有文档。两种卡都在最终答复结束本run；communicate可以先短说要整理什么，但不能用来提前发布完整文档或在后台等待确认。
用户可以继续补充或修改，每次修改产出新保存消息，旧内容和依据保留；新文档需重新认可。只有用户明确绑定当前真实messageId的确认才算认可，助手不能替用户确认；认可只核对需求，不是发布、付款或购买技术方案。
之后若用户想继续，只引导独立的模拟发布/测试付款操作，不代点击。POC无需平台注册登录；需求仅模拟发布，PayPal是Sandbox测试资金，弹窗可能仍需Sandbox买家登录。签约前可全额退款是演示规则，未实现真实签约/专家流程/真实发布；不编价格或交易结果。
